# المعمارية

## الصورة العامة

```text
المتصفح ──HTTPS──► بوابة الشركات (Nuxt/Nitro)  ─┐
                                                 ├─► Laravel API /api/v1 ──► PostgreSQL (Supabase)
المتصفح ──HTTPS──► لوحة الإدارة (Next.js)  ──────┘          │  └─► Redis (Queue/Cache/Horizon)
                                                            ├─► Supabase Storage (مستندات، شعارات، إيصالات)
                                                            ├─► FlightProviderInterface ──► Mock / مزود حقيقي لاحقاً
                                                            └─► Airlines API (بيانات شركات الطيران)
```

- **كل منطق الأعمال في Laravel**. الواجهتان لا تتصلان بقاعدة البيانات ولا تملكان أي مفتاح سري.
- **نمط BFF**: كل بوابة لها خادمها (Nitro / Route Handlers) الذي يحتفظ بتوكن Sanctum في كوكي
  `httpOnly; SameSite=Strict` على نطاق البوابة نفسها ويمرر الطلبات إلى الـ API. هذا يتيح النطاقات المخصصة
  للشركات (White-Label) دون كوكيز طرف ثالث، ويمنع JavaScript من قراءة التوكن.
- كل بوابة تمرر **قائمة مسارات مسموحة فقط**: بوابة الشركات لا تصل إلى `/admin/*` والعكس.

## عزل الشركات (Multi-Tenancy)

1. كل جدول خاص بالشركة يحمل `tenant_id` بمفتاح أجنبي.
2. الوسيط `tenant` يضبط `TenantContext` من المستخدم الموثّق **قبل** ربط النماذج بالمسارات،
   فيصبح أي سجل لشركة أخرى `404` لا `403` (لا يُكشف وجوده).
3. `BelongsToTenant` يضيف نطاقاً عاماً لكل استعلام، ويملأ `tenant_id` تلقائياً، ويرفض كتابة سجل لشركة أخرى.
4. داخل الشركة: سياسات (`BookingPolicy`) — من لا يملك `bookings.view_all` يرى حجوزاته فقط.
5. طبقة إضافية في PostgreSQL: RLS مفعّل على كل الجداول ومنع صلاحيات أدوار Supabase العامة.

## دورة الحجز

```text
pending ──hold──► on_hold ──issue (خصم)──► confirmed ──تذاكر من المزود──► ticketed ──► refund_pending ──► refunded
   │                │                         │  ▲                                          │
   ▼                ▼                         ▼  │ فشل مؤكد + المهلة سارية (عكس الخصم)        ▼
 failed       expired/cancelled          cancelled/failed                           ticketed (رُفض الاسترداد)
```

- **البحث**: يُرسل لكل مزود مفعّل يدعم نوع الرحلة؛ تُسعّر العروض وتُحفظ (ULID) لمدة 30 دقيقة.
- **قبل الحجز**: إعادة تسعير وتحقق من التوفر؛ إن تغيّر السعر يُرفض الطلب (`PRICE_CHANGED`) حتى يوافق الموظف على السعر الجديد.
- **الحجز المبدئي**: بعد التحقق من الرصيد+الائتمان، وفقط إذا كان المزود يدعم `hold`. انتهاء المهلة يُعالج كل دقيقة.
- **الإصدار**: قفل صف الحجز ← فحص الرصيد تحت القفل ← خصم وقيد وفاتورة ← طلب التذاكر من المزود.
  - نجاح بأرقام تذاكر ← `ticketed`.
  - فشل مؤكد ← قيد عكسي وإشعار دائن، وعودة إلى `on_hold` أو `failed`.
  - مهلة/نتيجة غير معروفة ← يبقى `confirmed / pending_verification` ويُتحقق لاحقاً من المزود؛ لا افتراض للنجاح أو الفشل.
- **منع التكرار**: ترويسة `Idempotency-Key` إلزامية لإنشاء الحجز والإصدار والاسترداد والدفعات، ومفاتيح فريدة في
  الجداول (`bookings`، `payments`، `ledger_transactions`)، وقفل الصفوف عند الخصم.

## المهام الخلفية

| المهمة | المشغّل |
|---|---|
| `ReconcileBooking` | بعد انقطاع أثناء الحجز المبدئي: البحث عن الحجز لدى المزود بمرجعنا |
| `VerifyTicketing` | بعد نتيجة إصدار غير معروفة: محاولات بتأخير متزايد ثم `needs_attention` |
| `SyncRefund` | استرداد قيد المعالجة لدى المزود |
| `GenerateBookingDocuments` / `GenerateInvoiceDocument` | إنشاء ملفات PDF وتخزينها |
| مجدول كل دقيقة | انتهاء الحجوزات المبدئية، تنبيه قبل الانتهاء بـ30 دقيقة، نبضة المجدول |

## التخزين

`FileStorage` بمحركين: `local` (تطوير/اختبار، `storage/app/private` مع روابط موقّعة) و`supabase` (حاويات خاصة
`documents` و`branding` و`payment-proofs`). الواجهات تحصل على الملفات عبر الـ API بعد التحقق من الصلاحية فقط.

## المستندات

قوالب Blade + mPDF (دعم كامل للعربية وRTL): تأكيد الحجز (يذكر دائماً أنه ليس تذكرة)، إيصال التذكرة الإلكترونية
(يُرفض إنشاؤه قبل وجود أرقام تذاكر من المزود)، الفاتورة والإشعار الدائن (بهوية المنصة لأنها بين المنصة والشركة).
